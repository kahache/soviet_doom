# Покрытие кода тестами

Живой документ (стабильное имя); измеряется заново каждый раз, когда CEO
или гейт запрашивает свежее число. Каноническая версия: `docs/qa/COVERAGE.md`
(английский) (D7). Инструментарий: `tools/coverage.sh`, `.coveragerc` (оба
в корне репозитория/`tools/`).

Синхронизировано с оригиналом: 2026-10-27.

`coverage` — инструмент **только для разработки** (dev-only),
устанавливается только внутри `.venv/`
(`.venv/bin/python -m pip install coverage` на Mac,
`.venv/Scripts/python.exe -m pip install coverage` на Windows).
`tools/build.py` как и прежде собирает `dist/sovietdoom.pk3`, используя
только stdlib, — это не изменилось и не должно измениться.

## Как это запустить

```bash
tools/coverage.sh                  # run the suite under coverage, print the report, write HTML
tools/coverage.sh --no-html        # same, skip the HTML report (faster)
bash tools/coverage.sh --no-html   # Windows: the same script under Git Bash
```

Это запускает `python -m unittest discover -s tests` под `coverage run
--branch`, затем `coverage report --sort=cover` (худший файл первым, итог
— последним) и `coverage html` в `logs/coverage/html/` (в .gitignore —
открыть `logs/coverage/html/index.html` локально, чтобы пройтись по
любому файлу). `COVERAGE_FILE` перенаправлен в `logs/coverage/.coverage`,
чтобы необработанные данные никогда не попадали в корень репозитория.
Скрипт находит интерпретатор из venv на любой из двух машин
(`.venv/bin/python`, иначе `.venv/Scripts/python.exe`); на Windows он
отработал без изменений 2026-10-13 (PM уже добавил путь для Windows).

Код возврата скрипта — это код возврата **набора тестов**, а не порог
покрытия: здесь нет гейта `fail_under` (см. «Чем этот отчёт не является»
ниже). Покрытие измеряется и выводится даже при падении тестов; падающий
тест всё равно выполняет код на пути к падению, и это выполнение тоже
засчитывается.

## Уровни тестов: что запускает `verify.py fast` и что ждёт `art` (2026-10-14, QA)

Покрытие не затронуто: `tools/coverage.sh` по-прежнему запускает весь набор
обычным `unittest discover`, так что каждое число ниже включает каждый тест.
Изменился `tools/verify.py`: набор теперь проходит через `tests/_tiers.py` —
единственное место, которое решает, к какому уровню относится каждый тест.

- **`fast`** запускает каждый найденный тест, кроме таблицы `SLOW` в
  `tests/_tiers.py` (57 записей: модули, классы или отдельные тесты, у
  каждой своя причина), с `SD_SKIP_SLOW_ART=1`, как и раньше. Он сохраняет
  тесты сборки и check_pk3, каждый текстовый/контрактный тест (LANGUAGE,
  MAPINFO, ZScript, UDMF, MENUDEF, лицензии, сам verify), планы карт (метро и
  завод, MAP02 и MAP03 с D62) и дешёвые контракты генераторов.
- **`art` и `full`** запускают **каждый** найденный тест. Сверх `fast` это
  добавляет рендеры генераторов (арт, звук, риг), релиз от начала до конца,
  оверлей черновиков, сканы work/, чтение gzdoom.pk3, геометрию линий
  видимости MAP01/полигона, `route.MapData` и повторные проверки целого PK3
  для наборов спрайтов.
- **Ничего не потеряно:** fast + (только art) = найдено.
  `python tests/_tiers.py --list` печатает разбиение. 2026-10-14 около
  19:50: найдено 1767 = 1283 fast + 484 только art. `verify.py art` несколькими
  минутами раньше прогнал 1750 из 1750 найденных (PASS, skipped=1, опциональный
  тест движка). На уровне `fast` «Ran» у unittest примерно на 16 меньше
  числа уровня: классы, у которых `setUpClass` пропускается при
  `SD_SKIP_SLOW_ART`, считаются один раз как пропуск, а не по тестам.
- **Кэш сборки:** 19 тестов собирали один и тот же PK3. Раннер оборачивает
  `sdbuild.pk3.build` на один процесс. Ключ — содержимое src/, assets/ и
  tools/, а дайджест неизменённого файла переиспользуется, пока его размер и
  mtime не меняются. `tests/test_build.py` обходит кэш, потому что тестирует
  сам сборщик (включая воспроизводимость). Прогон fast теперь собирает дважды
  и переиспользует шесть раз.
- **До → после**, ПК с Windows при работающих других агентах, подряд на одном
  дереве около 19:55: старый быстрый набор (`SD_SKIP_SLOW_ART=1 python -m
  unittest discover -s tests`, 1751 тест) занял **119 с** по часам. Новый
  `verify.py fast` (документы + сборка + check_pk3 + 1267 тестов) занял
  **14 с** (13,5 с VERDICT). Более ранние прогоны при большей нагрузке:
  16-19 с.
- **Как держать быстрым:** `python tests/_tiers.py fast --durations 15`
  называет самые медленные тесты уровня. Новый медленный класс идёт в `SLOW`
  с указанием причины. Если после переименования запись ни с чем не
  совпадает, `verify.py` показывает WARN на этапе тестов, потому что иначе
  этот класс молча вернулся бы в `fast`.

Медленные затраты, которые являются неэффективностью тестов, сообщены
владельцам файлов, а не исправлены здесь (QA не редактирует чужие тесты):
`test_art.ApprovedAssetsTests.test_identical_to_work_source` обходит rglob-ом
весь work/ один раз на каждый установленный PNG (26 с; один индекс work/ по
имени дал бы ~1 с). Модульные фикстуры `test_audition` считают SHA-256 всего
`work/audio` (296 МБ) дважды (~3 с; хватило бы дайджеста по stat).
`test_route.ParseTest` строит `route.MapData` для обеих карт в `setUpClass`
(9 с).

### Найденные ошибки (QA нашла, не исправляла)

**B4 (ЗАКРЫТА 2026-10-13 23:00: макет читает SkillMenu из MENUDEF;
ожидаемое падение ушло).** `gen_menu.py` рисует макет экрана сложности с
предлагаемой раскладкой `SUGGEST_HEADER = (48, 70)` и
`SUGGEST_ITEMS = (48, 90)`, а `src/lumps/MENUDEF` поставляет её как

числа «Engine geometry (src/lumps/MENUDEF ...)». Следствие: заново
сгенерированная развёртка меню рисует экран сложности, которого в игре
нет, а её проверка ширины печатает ложное переполнение. **Воспроизведение:**

failure` (`((32, 70), (32, 90)) != ((48, 70), (48, 90))`); и
`gen_menu.mock_skill("en", "suggest", ...)` возвращает
`["'Hero of the Soviet Union, posthumously' ends at x=336"]`.
**Ожидалось:** предлагаемая раскладка — из `MENUDEF`, без переполнения.
Закодировано как `@unittest.expectedFailure`; когда константы будут
исправлены, тест станет неожиданным успехом, и маркер надо будет снять.

## `.coveragerc`: что исключено и почему

```ini
[run]
source = tools
branch = True
omit = tests/*, .venv/*, work/*, */__pycache__/*

[report]
include_namespace_packages = True
exclude_also =
    if __name__ == .__main__.:
    def parse_args\(
```

- **`source = tools`, `omit = tests/*, .venv/*, work/*`**: мы измеряем
  собственный инструментарий, а не тестовый фреймворк, не виртуальное
  окружение и не черновики арта в работе (`work/` — черновое
  пространство в .gitignore, никогда не попадает в поставку).
- **`branch = True`**: CEO спросил именно о том, *какие ветки
  выполняются*, а не только какие строки — одно лишь покрытие строк
  скрыло бы `if`, у которого `else` никогда не срабатывает.
- **`if __name__ == .__main__.:`**: эта защита (и строка
  `sys.exit(main())`, которую она защищает) выполняется только тогда,
  когда файл запускается напрямую — `python3 tools/build.py`,
  `tools/run.sh`, `tools/smoke.py` из шелла. Набор тестов всегда
  импортирует эти модули по имени и вызывает `main()`/`build()` с явным
  `argv` — именно так их уже проверяют `tests/test_build.py` и
  `tests/test_smoke.py`. Сама по себе эта строка не содержит никакой
  логики.
- **`def parse_args\(`**: исключает чистую обвязку argparse, но
  **только** в двух файлах, где она аккуратно вынесена из логики в
  отдельную функцию `parse_args()` — `tools/check_pk3.py` и
  `tools/smoke.py`. Файлы, которые собирают свой парсер *прямо внутри*
  `main()`, вперемешку с реальной логикой (`tools/build.py`,
  `tools/art/gen_lenin.py`, `tools/art/make_preview.py`,
  `tools/audio/audition.py`, `tools/audio/gen_music.py` и инструменты,
  добавленные с тех пор), **намеренно не исключены**, потому что вырезать
  там только строки `add_argument` было бы ровно той косметической
  подчисткой, от которой этому отчёту прямо велели отказаться. Их
  пробелы учтены и разобраны как настоящие пробелы — связанные с CLI или
  нет.
- Больше ничего не исключено. `.coveragerc` не менялся с первого отчёта;
  ни одно исключение не добавлено, чтобы смягчить число для Windows.

**Одна настоящая ошибка, которую выявил первый отчёт, — исправленная, а не
заметённая под ковёр:** по умолчанию проход `coverage`, который «также
отчитывается о файлах, которые вообще никогда не выполнялись»
(`find_possibly_unexecuted_files` в `coverage/inorout.py`), пропускает
любую поддиректорию без `__init__.py`, если не выставлено
`[report] include_namespace_packages = True`. У `tools/art/` и
`tools/audio/` нет `__init__.py` (тесты импортируют их модули по
короткому имени через `sys.path.insert`, см. `tests/test_art.py`), так
что без этой одной строчки первый запуск этого инструмента молча
**прятал** семь целых файлов из отчёта, вместо того чтобы показать их
настоящие 0%. Итоговое число до исправления было **86%**; после — **58%**.
Этот разрыв — не ухудшение кода, а то, что измерение наконец увидело код,
к которому до этого было слепо. Тот же флаг делает видимыми и одиннадцать
файлов с 0% выше: без него этот отчёт показывал бы число намного выше — и
неверное.

## Честный анализ

### Проверка гипотезы CEO, второе измерение

**«`tools/sdbuild/` критически недопокрыт» — по-прежнему неверно в
среднем, по-прежнему верно в тех же трёх местах.** `sdbuild/udmf.py` — на
97% после роста на 63 строки (`tests/test_udmf.py` вырос вместе с ним),
`sdbuild/wad.py` — 87%, `sdbuild/pk3.py` — 84%. Внутри `pk3.py` три
**документированные, поддерживаемые и совершенно не выполненные** ветки,
названные в первом отчёте, по-прежнему не выполняются, сдвинулись только
номера их строк:

1. **Ветка `collect_maps()` для необработанного `.wad`** (теперь строки
   90-92): карта, положенная как `.wad` в `src/maps/` (экспорт из
   Ultimate Doom Builder), а не сгенерированная `map.py`. Под тестами не
   выполнялась.
2. **Ветка `collect_assets()` для отсутствующей директории** (теперь
   строка 150, `return []`) и, с ней, `tools/build.py --assets
   <отсутствующий путь>`, заявленный в `build.py --help`. Под тестами не
   выполнялась.
3. **Защита `collect_entries()` от дублирующихся путей** (теперь строка
   179, `raise BuildError(f"duplicate PK3 path ...")`). Под тестами ни
   разу не срабатывала.

**«Генераторы арта в `tools/art/` критически недопокрыты» — верно, и
разделительная линия сдвинулась.** В первом отчёте линия проходила между
выпущенным генератором batch 1 (93%) и всем более новым (0%). С тех пор
`gen_shell.py` (титры/меню/интермишн, D18) поднялся с 0% до 86%, а
`artlib.py` — с 91% до 99%, причём `save_indexed()` — функция, которая
обеспечивает «индексацию по палитре мода», — теперь тестируется
напрямую, что закрывает большую часть третьего пробела первого отчёта.
Новая линия проходит между ними и **тремя генераторами, стоящими за
ассетами, которые CEO уже одобрил или рассматривает, и у которых нет
вообще никаких тестов**: `gen_font.py` (0%, алфавит D24, который
поставляется в `assets/fonts/`), `gen_metro.py` (0%, batch 2) и
`gen_switch.py` (30%, переключатели, уже лежащие в `assets/`, у которых
`main()` и путь отрисовки не протестированы). `tools/audio/` — на 0% во
всех пяти файлах; три из них новые с момента прошлого отчёта.

### Подтверждение другой половины: ветки CLI и ошибок, которые не так важны

- **Пробел `tools/smoke.py`** по-прежнему — собственно запуск движка в
  `main()`, обоснованно оставленный опциональному тесту
  `SD_ENGINE_TESTS=1` и прогонам движка у PM (D26: агенты больше вообще
  не запускают GZDoom).
- **`tools/verify.py` на 68%** новый и пришёл с 556-строчным тестовым
  файлом; его 110 недостающих выражений в этом проходе не
  перечислялись, и их безобидность не утверждается. Следующее измерение
  должно на них посмотреть.
- **Оставшиеся пробелы `tools/build.py` и `tools/check_pk3.py`** — в
  основном ветки форматирования вывода и второстепенные пути ошибок у CLI,
  чья основная логика тщательно проверяется. Низкая ценность погони за
  этим.
- **Шесть пробелов `tools/sdbuild/wad.py`** — все это защиты `raise
  WadError(...)`, каждую закрывает одна строка `assertRaises`. Не срочно.

## Три пробела, которые важны больше всего

Ранжировано по критерию «регрессия здесь уйдёт в релиз молча, и никто не
узнает, пока человек не наткнётся на неё в игре или в логе сборки»:

1. **`tools/art/gen_font.py`, 0% из 791 выражения.** Самый большой файл в
   `tools/`, порождающий 214 глифов, благодаря которым D7 и D21 возможны
   в игре (D24). Его вывод сегодня лежит в `assets/fonts/`. Единственный
   тест, который смотрит на эти глифы (`test_identical_to_work_source`),
   сравнивает байты с `work/art/font/`, а её на рабочей машине нет,
   поэтому он пропускается (B3). Регрессию в генераторе — глиф вне
   палитры, неверный размер ячейки, пропавший кодпоинт — не поймало бы
   ничто, пока кто-нибудь не прочтёт меню в игре.
   *Тест, который закрыл бы это:* запустить генератор для одного
   варианта во временную директорию (как `ShellTests` делает для
   `gen_shell.build()`), затем проверить число глифов на размер, что цвет
   каждого непрозрачного пикселя ⊆ `docs/art/palette.json` при альфе только
   0 или 255 (шрифты-папки по замыслу RGBA, `docs/art/ART-BIBLE.md` §2, а не
   режим `P`; сейчас за этим следит `InstalledGlyphPaletteTests` в
   `tests/test_gen_font.py`), и размеры ячеек, которые объявляет раскладка
   шрифта в `docs/engine/MOD-SPEC.md`.

2. **Три ветки `sdbuild/pk3.py` (90-92, 150, 179)**, без изменений с
   первого отчёта и по-прежнему не протестированные после второго
   измерения: путь карты как необработанного `.wad`, путь
   отсутствующей `assets/` и защита от дублирующихся путей. Три
   небольших теста, описанных в первом отчёте, по-прежнему не написаны:
   крошечная PWAD-фикстура с именем `MAPXX.wad` в `src/maps/` без
   соседнего `map.py`; `build(..., assets=tmp / "does-not-exist")`; и две
   записи с одинаковым путём через `collect_entries()` с проверкой
   `BuildError`.

3. **`main()` и путь отрисовки `gen_switch.py` (30%) и `main()` у
   `gen_soviet_base.py` (469-492).** У обоих генераторов есть ассеты в
   `assets/`, одобренные CEO; сквозной путь записи ни одного из них не
   выполняется набором тестов. `artlib.save_indexed()` теперь
   тестируется изолированно, что убирает худший риск (PNG без
   индексации), но циклы, выбирающие имена, размеры и поля манифеста, по-
   прежнему не выполняются.
   *Тест, который закрыл бы это:* `main()` с `OUT_DIR`/`MANIFEST`,
   перенаправленными во временную директорию, как `tests/test_art.py`
   уже делает для помощников `gen_soviet_base`, с проверкой числа
   файлов, размера, режима и полей манифеста, которые читают
   `make_preview.py`/`check_pk3.py`.

(Четвёртый, названный потому, что исправление — одна строка: **B3**
выше. Пока условие пропуска в `test_identical_to_work_source` ищет
рендер batch, а не `work/`, быстрый цикл на Windows в одном запуске
генератора от красного.)

## Чем этот отчёт не является

- **Не новый гейт.** Фиксированный порог (`fail_under`) не задан. CEO
  попросил реальное число, а не строку pass/fail; владельцы определений
  гейтов — `docs/ROADMAP.md` и `docs/PRD.md`, и добавление туда гейта по
  покрытию — это продуктовое решение CEO, а не то, что этот отчёт решает
  самостоятельно.
- **Не новые тесты.** В этом проходе ни одного не написано (бриф
  перехода на Windows запрещал трогать `tests/`). Пробелы выше описаны
  достаточно подробно, чтобы их написать: `mod-engineer` для `sdbuild/`,
  `art-director` для `tools/art/`, `sound-designer` для `tools/audio/`.
- **Не число для Mac.** 49% — это то, что это дерево показывает на ПК с
  Windows при отсутствующей `work/`. То же дерево на Mac читалось бы
  примерно до ~1,5 пункта выше (`gen_lenin.py`); это не измерялось и не
  утверждается.
- **Не вердикт об одном коммите.** На момент измерения в рабочем дереве
  были незакоммиченные изменения инструментария (перечислены выше);
  число привязано к коммиту перехода на Windows, который последует, какой
  бы хеш он ни получил.
