# Покрытие кода тестами

Живой документ (стабильное имя); измеряется заново каждый раз, когда CEO
или гейт запрашивает свежее число. Каноническая версия: `docs/qa/COVERAGE.md`
(D7). Инструментарий: `tools/coverage.sh`, `.coveragerc` (оба в корне
репозитория/`tools/`).

`coverage` — инструмент **только для разработки** (dev-only),
устанавливается только внутри `.venv/`
(`.venv/bin/python -m pip install coverage`). `tools/build.py` как и
прежде собирает `dist/sovietdoom.pk3`, используя только stdlib, — это не
изменилось и не должно измениться.

## Как это запустить

```bash
tools/coverage.sh            # запускает набор тестов под coverage, печатает отчёт, пишет HTML
tools/coverage.sh --no-html  # то же самое, но без HTML-отчёта (быстрее)
```

Это запускает `python3 -m unittest discover -s tests` под `coverage run
--branch`, затем `coverage report --sort=cover` (худший файл первым, итог
— последним) и `coverage html` в `logs/coverage/html/` (в .gitignore —
открыть `logs/coverage/html/index.html` локально, чтобы пройтись по
любому файлу). `COVERAGE_FILE` перенаправлен в `logs/coverage/.coverage`,
чтобы необработанные данные никогда не попадали в корень репозитория.

Код возврата скрипта — это код возврата **набора тестов**, а не порог
покрытия: здесь нет гейта `fail_under` (см. «Чем этот отчёт не является»
ниже). Покрытие измеряется и выводится даже при падении тестов; падающий
тест всё равно выполняет код на пути к падению, и это выполнение тоже
засчитывается.

## `.coveragerc`: что исключено и почему

```ini
[run]
source = tools
branch = True
omit = tests/*, .venv/*, work/*, */__pycache__/*

[report]
include_namespace_packages = True
exclude_also =
    if __name__ == .__main__.:
    def parse_args\(
```

- **`source = tools`, `omit = tests/*, .venv/*, work/*`**: мы измеряем
  собственный инструментарий, а не тестовый фреймворк, не виртуальное
  окружение и не черновики арта в работе (`work/` — черновое
  пространство в .gitignore, никогда не попадает в поставку).
- **`branch = True`**: CEO спросил именно о том, *какие ветки
  выполняются*, а не только какие строки — одно лишь покрытие строк
  скрыло бы `if`, у которого `else` никогда не срабатывает.
- **`if __name__ == .__main__.:`**: эта защита (и строка
  `sys.exit(main())`, которую она защищает) выполняется только тогда,
  когда файл запускается напрямую — `python3 tools/build.py`,
  `tools/run.sh`, `tools/smoke.py` из шелла. Набор тестов всегда
  импортирует эти модули по имени и вызывает `main()`/`build()` с явным
  `argv` — именно так их уже проверяют `tests/test_build.py` и
  `tests/test_smoke.py`. Сама по себе эта строка не содержит никакой
  логики.
- **`def parse_args\(`**: исключает чистую обвязку argparse, но
  **только** в двух файлах, где она аккуратно вынесена из логики в
  отдельную функцию `parse_args()` — `tools/check_pk3.py` и
  `tools/smoke.py`. Пять других файлов собирают свой парсер *прямо
  внутри* `main()`, вперемешку с реальной логикой (`tools/build.py`,
  `tools/art/gen_lenin.py`, `tools/art/make_preview.py`,
  `tools/audio/audition.py`, `tools/audio/gen_music.py`): они
  **намеренно не исключены**, потому что вырезать там только строки
  `add_argument` было бы ровно той косметической подчисткой, от которой
  этому отчёту прямо велели отказаться. Их пробелы учтены и разобраны
  ниже как настоящие пробелы — связанные с CLI или нет.
- Больше ничего не исключено. Защитного `except ImportError` fallback
  нигде внутри `tools/` не существует (проверено), так что и для этого
  распространённого исключения не нашлось ни одного кандидата.

**Одна настоящая ошибка, которую это выявило, — исправленная, а не
заметённая под ковёр:** по умолчанию проход `coverage`, который «также
отчитывается о файлах, которые вообще никогда не выполнялись»
(`find_possibly_unexecuted_files` в `coverage/inorout.py`), пропускает
любую поддиректорию без `__init__.py`, если не выставлено
`[report] include_namespace_packages = True`. У `tools/art/` и
`tools/audio/` нет `__init__.py` (тесты импортируют их модули по
короткому имени через `sys.path.insert`, см. `tests/test_art.py`), так
что без этой одной строчки первый запуск этого инструмента молча
**прятал** семь целых файлов — `gen_lenin.py`, `gen_shell.py`,
`make_contact.py`, `make_preview.py`, `emblem_check.py`, `audition.py`,
`gen_music.py` — из отчёта, вместо того чтобы показать их настоящие 0%.
Итоговое число покрытия до исправления было **86%**; после — **58%**.
Этот разрыв в 28 пунктов — не ухудшение кода, а то, что измерение
наконец увидело код, к которому до этого было слепо. Это ровно тот
режим отказа, от которого предостерегал бриф, только в противоположном
направлении от «раздувания числа исключением реальных пробелов» —
оставленная настройка по умолчанию раздула бы его, *пряча* файлы
целиком. Любой, кто перезапустит `coverage` вручную без этого
`.coveragerc`, получит обманчиво радужное число.

## Честный анализ

### Проверка гипотезы CEO

**«`tools/sdbuild/` критически недопокрыт» — неверно в среднем, верно в
двух конкретных местах.** `sdbuild/udmf.py` — лучше всех протестированный
файл во всём дереве (98%, только что появились 41 специально написанных
тест). `sdbuild/wad.py` (87%) и `sdbuild/pk3.py` (84%) надёжно покрыты на
своём основном пути — том самом, который реально проходит каждый запуск
`tools/build.py`. Но внутри `sdbuild/pk3.py` за этими солидными 84%
прячутся три **документированные, поддерживаемые и совершенно не
выполненные** ветки:

1. **Ветка `collect_maps()` для необработанного `.wad`** (строки 85-86):
   собственный docstring модуля говорит, что карта может прийти либо как
   `src/maps/<MAP>/map.py` (сгенерированная), *либо* как
   `src/maps/<MAP>.wad` (скопированная как есть, например, экспорт из
   Ultimate Doom Builder). Под тестами хоть раз выполнялся только первый
   путь. Если level-designer начнёт экспортировать из UDB, это будет
   первый раз, когда этот код реально выполнится.
2. **Ветка `collect_assets()` для отсутствующей директории** (строка
   126) и, с ней, `tools/build.py --assets <отсутствующий путь>` —
   заявленная в собственном тексте `--help` у `build.py` как «передайте
   несуществующий путь, чтобы собрать без арта», и это ровно то
   состояние, в котором проект находился большую часть F0/F1. Никогда
   не протестирована.
3. **Защита `collect_entries()` от дублирующихся путей** (строка 150):
   проверка, которая не даёт двум файлам молча столкнуться по одному и
   тому же пути в PK3. Это защита такого рода, которая существует
   *потому что* нечто подобное уже однажды пошло не так (см. заметку
   docstring `collect_assets` «blocker M1, found by level-designer
   2026-10-12») — и она ни разу не срабатывала под тестами.

Ничего из этого не видно в 84% файла; агрегированное число это скрывает.

**«Генераторы арта в `tools/art/` критически недопокрыты» — верно, но
резко разделено по возрасту.** `gen_soviet_base.py` — скрипт, стоящий за
9 текстурами batch 1, одобренными CEO, — хорошо протестирован на 93%, и
не поверхностно: `tests/test_art.py` проверяет его вспомогательные
функции `quantize`/`Overlay`/`ramp_colour` на реальном пиксельном
выводе, ограничениях палитры и математике бесшовности (tiling-seam).
Чего он *не* тестирует — это сам `gen_soviet_base.main()` (684-710) —
цикл, который реально записывает PNG и JSON-манифест, — а значит, и
`artlib.save_indexed()` (функцию, которая обеспечивает «индексацию по
палитре мода», один из буквальных критериев гейта в QA-брифе
`CLAUDE.md`), и `artlib.tiling_seam_score()`. Любой *другой* генератор
арта — `gen_shell.py` (экраны титров/меню/интермишна, 350 выражений),
`gen_lenin.py` (плакат с Лениным), `make_contact.py`, `make_preview.py`,
`emblem_check.py` — сидит на буквальных, безоговорочных 0%. Это более
новые инструменты (F3/F4, «выполняются параллельно» согласно собственной
строке статуса в `CLAUDE.md`), которые просто ещё не получили столько же
инвестиций в тесты, сколько уже выпущенный batch. `tools/audio/`
(`audition.py`, `gen_music.py`) на 0% по той же причине — им на момент
написания один день (D16, 2026-10-13).

### Подтверждение другой половины: ветки CLI и ошибок, которые не так важны

- **Большой пробел `tools/smoke.py` (строки 455-551)** — это собственно
  запуск движка внутри `main()`: сборка командной строки, запуск
  настоящего GZDoom как подпроцесса, чтение его лога, вывод сводки,
  определение кода возврата. Для этого нужен настоящий бинарник GZDoom
  и дисплей; это обоснованно оставлено на опциональный
  `test_smoke_run_passes_on_the_current_pk3` (по умолчанию пропускается,
  `SD_ENGINE_TESTS=1` — чтобы запустить его по-настоящему) и на ручные
  прогоны с доказательствами, которые QA уже делает через `tools/run.sh`.
  Каждый фрагмент логики, который *питает* этот блок — `scan_log()`,
  `find_gzdoom()`, `find_iwad()`, обработка таймаута — уже имеет
  собственные выделенные тесты в `tests/test_smoke.py`. Единственный
  кусок реальной, непротестированной логики, зарытый в этом блоке, — это
  финальная цепочка if, которая превращает `Report` в один из
  `EXIT_TIMEOUT` / `EXIT_LOG_FAILURES` / `EXIT_ENGINE_FAILED` /
  `EXIT_NO_MAP` / `EXIT_OK` — см. список «пробелы, которые важны» ниже.
- **Оставшиеся пробелы `tools/build.py` и `tools/check_pk3.py`** — это в
  основном ветки форматирования вывода (сводка `build.py` по умолчанию,
  без `--quiet`; читаемый человеком рендер отчёта в `check_pk3.py`,
  который уже проверен поле за полем в 26 КБ `tests/test_check_pk3.py`)
  и второстепенные пути ошибок у CLI, чья основная логика проверок уже
  тщательно протестирована. Низкая ценность погони за этим.
- **Пять пробелов `tools/sdbuild/wad.py`** (строки 57, 64, 93, 96, 111)
  — все это защиты `raise WadError(...)` в 18-строчном бинарном
  писателе/читателе: реальные, но тривиально мелкие и изолированные
  (каждую закрывает одна строка `assertRaises`). Не срочно, не
  критично.

## Три пробела, которые важны больше всего

Ранжировано по критерию «регрессия здесь уйдёт в релиз молча, и никто не
узнает, пока человек не наткнётся на неё в игре или в логе сборки»:

1. **`sdbuild/pk3.py::collect_maps()`, ветка для карты как
   необработанного `.wad` (строки 85-86).** Документированный,
   поддерживаемый способ передать карту в builder (экспорт из Ultimate
   Doom Builder, положить `.wad` в `src/maps/`) ни разу не выполнялся
   под тестами.
   *Тест, который закрыл бы это:* положить крошечную, валидную
   PWAD-фикстуру (собранную с помощью `sdbuild.wad.build_pwad`, как
   `tests/test_check_pk3.py` уже делает для своих собственных фикстур)
   по пути `src/maps/MAPXX.wad` без соседнего `map.py`, вызвать
   `collect_maps()`/`build()` и убедиться, что она упакована в
   `maps/MAPXX.wad` байт-в-байт, плюс второе утверждение, что
   смешивание карты `map.py` и карты как необработанного `.wad` в одной
   сборке даёт обе.

2. **`sdbuild/pk3.py::collect_assets()`, ветка для отсутствующей
   директории `assets/` (строка 126) — а значит, и `tools/build.py
   --assets <отсутствующий>`.** Это не гипотетическая ситуация: это
   ровно то состояние, в котором проект находился большую часть F0/F1,
   и `build.py --help` рекламирует это («передайте несуществующий путь,
   чтобы собрать без арта»). Сейчас никто не вызывает `build()` с
   несуществующим путём `assets`.
   *Тест, который закрыл бы это:* `build(src, out, tools_dir,
   assets=tmp_path / "does-not-exist")` и проверка, что он всё равно
   производит PK3, содержащий только собственный контент `src/`, без
   исключения и без молчаливого создания на диске пустой папки текстур.

3. **`gen_soviet_base.py::main()` (684-710) и `artlib.save_indexed()`
   (272-277) — реальный путь записи PNG и манифеста.** Всё, что
   вызывает эта функция (`quantize`, `Overlay`, `ramp_colour`,
   `tiling_seam_score`), хорошо протестировано изолированно; функция,
   которая связывает всё это вместе, записывает `SD*.png` на диск с
   индексацией по палитре мода и пишет JSON-манифест рядом с `palette`,
   никогда не выполнялась под набором тестов. Сегодня она проверяется
   только постфактум — `check_pk3.py` сканирует файлы, уже попавшие в
   `assets/`, и человек смотрит на HTML-превью. Регрессия здесь
   (например, текстура, молча сохранённая без индексации, или манифест,
   потерявший поле, на которое опираются `check_pk3`/`make_preview.py`)
   не была бы перехвачена ни одним из текущих зелёных тестов.
   *Тест, который закрыл бы это:* запустить `gen.main()` с `OUT_DIR`,
   подменённым (monkeypatch) на временную директорию, затем проверить,
   что каждая запись `TEXTURES` произвела файл с ≤256 цветами палитры
   (`Image.open(p).getcolors()`), заявленной шириной/высотой, и что в
   `manifest.json` ровно столько же записей, сколько в `TEXTURES`, с
   полями, которые читают `make_preview.py`/`check_pk3.py`.

(Четвёртый, менее значимый пробел стоит назвать, поскольку каждый
исправляется одной строкой: у пяти защит `WadError` в `sdbuild/wad.py`
— пустой список лампов, не-`bytes` данные лампа, обрезанный blob,
неверная магия, отсутствующее имя лампа — на всех нет ни одного теста.
Любая из них — это один вызов `self.assertRaises(WadError, ...)`.)

## Чем этот отчёт не является
